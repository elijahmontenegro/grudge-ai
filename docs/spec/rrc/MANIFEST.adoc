== Context

=== Identity

*Name:* {project-name} {module-name}

*Paradigm:* Algorithm Library (stateful or stateless depending on caller)

The RRC engine is a Go library implementing the {rrc-full} algorithm. It operates on data structures (prerequisite DAG, QUD graph, score cache) provided by the caller. The engine reads and writes these structures but does not own them.

Two modes:

- **Stateful (agent path):** The service provides persistent data structures. The DAG, score cache, and QUD graph accumulate across requests. Carry-forward compounds. This is the full RRC experience.
- **Stateless (proxy path):** The service provides ephemeral data structures per-request. The engine scores, selects, assembles, and returns. Nothing persists. Each request is independent.

The engine does not know which mode it's running in. It operates on whatever structures the caller provides.

=== Stack

*Language:* {lang}

*Dependencies:* `proto/gen/go/grudge/v1` (proto types), standard library. No dependency on `spec/core`. The engine defines its own consumer interfaces (Scorer, Completer) -- any core adapter satisfies them via Go structural typing.

=== Scope

==== In Scope

- Prerequisite detection: cross-encoder pairwise dependency classification on message arrival, scored globally across all threads
- QUD (Questions Under Discussion) graph: per-thread, built from warm carry-forward, not dedicated LLM calls
- Prerequisite DAG: global dual adjacency list, incremental edge construction, thread-scoped or global subgraph extraction
- Score cache operations: reading and writing cross-encoder pairwise scores (global)
- Warm carry-forward ingestion: accepting extracted reasoning from the service, updating QUD graph and DAG
- Selection scoring: score fusion (cross-encoder + QUD + temporal proximity), thresholds, ranking
- Payload assembly: best-first backward traversal, ranked selection, native format restoration
- Transitive reduction: computed on demand during subgraph extraction

==== Out of Scope

- Calling LLMs (the service makes LLM calls; the engine receives extracted reasoning via carry-forward)
- Ownership or persistence of data structures (belongs to `spec/service`)
- Response stream parsing (belongs to `spec/service`; the engine receives extracted reasoning)
- HTTP proxy or network concerns (belongs to `spec/service`)
- Agent orchestration (belongs to `spec/service`)
- Conversation storage (belongs to `spec/service`)
- Interface definitions for LLM, embedder, or scorer (core interfaces belong to `spec/core`; the engine defines its own consumer interfaces)
- UI or introspection presentation (belongs to `spec/web`)
- Model selection, sizing, deployment topology, or fine-tuning

=== Error Types

Sentinel errors. Fail fast -- the engine does not retry.

[source,go]
----
var (
    ErrScorerFailed = errors.New("scorer returned error during scoring")
    ErrCompleterFailed  = errors.New("small model failed during QUD extraction")
    ErrMessageNotFound  = errors.New("message ID not found in data structures")
    ErrThreadNotFound   = errors.New("thread ID not found in data structures")
)
----

**Method-to-error mapping:**

- `OnMessage` → `ErrScorerFailed` (scorer error during pairwise scoring)
- `Select` → `ErrMessageNotFound` (promptID not in DAG), `ErrThreadNotFound` (threadID not in QUD graphs, when scope is thread-scoped)
- `CarryForward` → `ErrScorerFailed` (cross-encoder on thinking text), `ErrCompleterFailed` (small model QUD extraction)
- `Fork` → `ErrThreadNotFound` (parentThreadID not found)
- `Merge` → `ErrThreadNotFound` (parentThreadID not found)

`Select` with `SELECTION_SCOPE_ALL_THREADS`: `threadID` is empty string, ignored. With `SELECTION_SCOPE_THREAD`: `threadID` is required, `ErrThreadNotFound` if absent.

=== Concurrency

The Engine is NOT goroutine-safe. The caller (service) is responsible for serializing access. Concurrent reads and writes to the same Engine instance are undefined behavior.

The service uses RWMutex on the global DAG and score cache for concurrent selection reads and exclusive scoring writes. Per-thread QUD graphs are naturally isolated.

=== Complexity Bounds

- **OnMessage:** O(N) scorer calls where N is corpus size. Paid once per message arrival; results cached forever.
- **Select:** O(V+E) traversal where V is selected messages and E is their edges. Bounded by score floor.
- **CarryForward:** O(1) scorer call + O(1) completer call per thinking block (cross-encoder on thinking text + small model QUD extraction).
- **Transitive reduction:** O(V·E) on the selected subgraph (V typically ≤30, E typically <100).

Performance optimization is explicitly deferred. Correctness and completeness are the targets. O(N) pairwise scoring per message arrival is the accepted cost of prerequisite detection accuracy. The system may be slow; it must not be wrong.

=== Local Context (the In-Flight Window)

Added 2026-07-08, amended same day (A2) after live verification; see
docs/plan-iterations/2026-07-08-rrc-local-context-remediation.md. This section is
normative: the earlier absence of a Local Context definition is the vacuum the
implementation drifted into (backward anchor-reach, text-only anchoring, blob
chunking, turn-only delivery -- all removed).

Local Context is the in-flight WINDOW: the immediately preceding turn UNION the
current turn record, each turn-complete, all block types. It serves BOTH consumers.
The network sees the window whole -- tools included, through exact protocol closure
-- so the model is never blind to the exchange it is continuing (measured failure of
turn-only delivery: asked "what was the output of that command you just ran?", the
model received none of the preceding exchange and confabulated). The RRC engine takes
membership, exclusion, and mass-walk seeding from the window, while the QUERY is the
CURRENT turn's *semantic* projection: user text, assistant text, and thinking --
co-equal, uniformly treated. Thinking is the primary disambiguation signal (the model
is the best QUD analyzer in the system); no code path may privilege one semantic
block type over another. Images, attachments, and tool calls/results are NOT
semantic; whatever matters about them re-enters the discourse through the model's
thinking and response.

Four distinct roles, one shared object:

[cols="1,1,2"]
|===
| Role | Owner | Content

| Scoring query (disambiguation)
| serialized Local Context chunks (turn-discriminated)
| the CURRENT turn's semantic messages, ONE QUERY UNIT PER MESSAGE -- a chunk never
  spans two messages; the selection aggregator max-merges per candidate over units,
  so the message that bears the query dominates instead of being blended with
  neighbors. The window-tail contributes NO query text -- prior turns already spent
  their selections.

| Membership (exclusion, audit)
| serialized Local Context message ids
| every window id, tools and tail included -- nothing delivered is ever re-retrieved

| Wire delivery (native restoration)
| the window
| the preceding turn and the current turn verbatim, through exact protocol closure

| Graph-walk entry (mass recall)
| the window's membership, as walk seeds
| the delivered set seeds the provenance walk; the TAIL is the graph's entry point
  for a fresh turn (its own messages have no incoming provenance edges until it
  generates). Delivered never surfaces from the walk -- its yield is the window's
  undelivered ancestry, at banked mass.
|===

The QUERY is bounded by the turn, built FORWARD: the trigger queries at its call, the
flushed thinking queries at the next call (disambiguation compounds across calls via
carry-forward), the response concludes the record. A lone user question is a complete,
valid query. The anchor is the last SEMANTIC message of the current turn -- the
discourse focus -- never a trailing tool block.

*Inferences are perishable; observations keep* -- the anti-laundering invariant. A
derived value (calibrated P, effective score, MMR rewrite) may be consumed only
within the selection event that produced it; anything consumed later must be an
OBSERVATION (raw sim, raw evidence weight) interpreted by the CURRENT instrument.
Two instances are load-bearing. Provenance weights record raw evidence only: a
turn's own record banks at 1.0; a selected prerequisite banks the product of raw
cross-encoder scores along its via-path -- never the calibrated, mass-lifted, or
MMR-rewritten effective score (banking the lift fed it back into the next turn's
mass: a measured self-reinforcing echo). And DAG traversal beyond hop 1 derives
dependency strength from the recorded observation under the current calibrator at
mass zero -- consuming the stored formation verdict fossilized old circumstance
(the mass that justified delivery into THAT turn) and old coefficients into the
transitive pull; deriving at read time makes calibration genuinely retroactive (a
curve refit re-gates all history with no rewrite). Hop-1 seed edges are this
event's own fresh verdicts -- circumstance prices entry into the present turn
exactly once. The window-tail banks NOTHING: an edge that would exist for every
turn regardless of content encodes zero information.

Rejected anti-patterns (each was implemented once and measurably harmful; do not
reintroduce):

- **Backward positional reach into the QUERY** (grabbing a prior turn's message to
  "complete" it): pasted an off-topic neighbor into a recall query and suppressed the
  true prerequisite below the acceptance floor (0.84 solo -> 0.46 blended). It was
  also, covertly, the only delivery of the preceding exchange -- delivery belongs to
  the window, in the network layer, not inside the query object.
- **Turn-only delivery** (pruning the window to the current turn): blinds the model
  at every turn seam; the deictic follow-up cannot be answered by retrieval because
  deixis shares no content with its referent.
- **Blob chunking** (concatenate the span, slice by size): fuses messages and defeats
  the max-merge.
- **Text-over-thinking anchoring**: thinking is a full semantic anchor.
- **Recorded lineage edges into a trigger, and window-tail contributor edges**:
  nothing generated the trigger, and adjacency holds for every turn regardless of
  content -- temporal succession must never become scored graph weight. The tail is
  a walk seed, never a recorded edge.
- **Consuming stored inferences as evidence** (banking effective scores as
  provenance weight; chaining formation-time verdicts in traversal): the lift
  launders into the record or into the transitive pull and self-reinforces or
  fossilizes; after its own event, only a raw observation may be consumed, and
  always under the current calibrator.

=== Prerequisite Detection

==== Cross-Encoder Pairwise Dependency Classification

A single cross-encoder scores the dependency relationship between two messages. One model, one forward pass per pair, via the core scorer interface.

When message M_n arrives, the cross-encoder evaluates every (M_i, M_n) pair for i < n — across ALL threads, not just the thread M_n belongs to. Scoring is global because dependency does not respect organizational boundaries. A message in "backend architecture" may depend on a decision made in "project planning." Each pair produces a dependency score. Pairs scoring above threshold become edges in the prerequisite DAG.

The cross-encoder captures multiple facets of dependency implicitly through a single classification:

- **Entity reference dependency** (coreference) -- "that function" in M_n refers to something defined in M_i
- **Discourse dependency** (elaboration, cause, instantiation) -- M_n elaborates on, is caused by, or instantiates M_i
- **Logical prerequisite** -- M_n cannot be understood without M_i

These are not separate operations. They are theoretical lenses from NLP research (coreference resolution, PDTB discourse relations, prerequisite chain learning) that explain WHY the cross-encoder's entailment signal captures dependency. The model does not know these categories exist. It takes two texts in, classifies their logical relationship, outputs class probabilities.

Off-the-shelf NLI (Natural Language Inference) cross-encoders classify: entailment, contradiction, neutral. Entailment approximates dependency. Contradiction approximates non-dependency. Neutral approximates unrelated. No fine-tuning required.

Research basis: NLI cross-encoders (DeBERTa-v3 family), PDTB discourse relation framework, coreference resolution (CODI-CRAC), prerequisite chain learning (Liang et al., Gordon et al.).

==== QUD (Questions Under Discussion) Graph

The QUD graph captures what the cross-encoder cannot: long-range structural dependency through a thread's question-answer flow.

Every message addresses an implicit question and may raise new ones. If message M_47 raises a question and message M_312 answers it, M_47 is a prerequisite of M_312 -- even if they share no surface similarity and the cross-encoder would not score them highly as a pair.

The QUD graph is NOT built by dedicated LLM calls. It builds organically from warm carry-forward. The model is already the best QUD analyzer in the system -- it reasons about the conversation on every request. Its thinking blocks expose reasoning that disambiguates and contains QUD information. Making that reasoning a signal source is the mechanism.

The QUD graph is per-thread. Carry-forward only enriches the thread where the prompt originated. This preserves thread identity -- each thread develops its own reasoning trajectory through its own QUD accumulation. The cross-encoder handles cross-thread dependency; the QUD graph handles within-thread structural flow.

The graph starts cold. First few requests have no carry-forward data -- the cross-encoder is the only signal. As the model responds and reasoning accumulates, QUD edges appear and the graph gets richer. Natural warm-up, no bootstrapping needed.

QUD graph state:

- QUDs: question text, established-by message, parent QUD, status (open/partially-addressed/resolved), addressed-by messages
- Active stack: open QUDs ordered by recency
- Resolved set: closed QUDs retained for graph completeness
- Derived edges: source message -> target message, via QUD, with type (establishes->addresses, raises->resolves)

Research basis: Roberts (1996) QUD stack theory, Riester (2019) QUD tree construction, Benz & Jasinskaja (2017) mapping discourse relations to QUD.

=== Data Structures

The engine operates on three data structures. The service owns their persistence; the engine reads and writes them. Scoring and the DAG are global (across all threads). The QUD graph is per-thread.

==== Score Cache (global)

Cross-encoder pairwise dependency scores across all threads. When message M_n arrives, the engine scores every (M_i, M_n) pair across all threads and writes results to the cache. At query time, scores are already available -- no cross-encoder inference needed.

Messages are immutable. Cached scores do not become stale.

==== QUD Graph (per-thread)

Structural compression of a thread's discourse flow. One QUD graph per thread. Built incrementally from warm carry-forward as the model responds within that thread. Carry-forward only enriches the originating thread's graph -- this preserves thread identity.

Starts empty per thread. Grows richer with use.

==== Prerequisite DAG (global)

The central data structure. Cross-encoder edges (global) and QUD edges (per-thread) both feed into it. The DAG spans all threads.

**Structure:** Dual adjacency list -- two indexes over the same edge set:

- **Backward:** message -> its prerequisites (messages it depends on). The primary traversal direction for RRC.
- **Forward:** message -> its dependents (messages that depend on it). Used for impact analysis and introspection.

Edges carry: source, target, score, detection source (cross-encoder, QUD, or both), timestamp.

Temporal ordering guarantees acyclicity: edges only point from earlier messages to later messages. No cycle detection needed.

The engine defines the in-memory structures. The service decides how to persist and restore them.

=== Forked Threads (Subagents)

The engine supports ephemeral thread forks for subagent execution. A fork inherits a snapshot of the parent thread's DAG and score cache at fork time. The forked thread runs RRC per-event against its own corpus (parent's messages at fork time + its own new messages). Carry-forward builds its own QUD graph — identity diverges.

On merge: the fork's messages and edges enter the parent's corpus. Cached scores transfer (messages are immutable). The parent only needs to score the fork's messages against any parent messages that arrived after the fork. The fork's QUD graph does not merge — the parent builds its own understanding of the fork's output through carry-forward.

The engine does not know about "subagents." It operates on threads — fork is a thread created from another thread's snapshot. Merge is messages and edges entering the parent thread's data structures. The service orchestrates the fork/merge lifecycle.

=== Selection Scoring

==== Calibrated Acceptance and the Budget-Price Law

(Replaced 2026-07-09. The prior Score Fusion section documented the retired
pre-A4 mechanism -- NLI entailment scores, hand-set fusion weights
(w1/w2/w3), a temporal-proximity term, a flat edge threshold. NLI was found
insufficient and removed; temporal-as-edge-signal was rejected as
duplicating Local Context's job; hand weights and flat thresholds are rules
where laws belong.)

Acceptance is one law: *P(prereq | signals) >= LossRatio + mu*tokens*.

- **P** fuses the raw signals -- semantic similarity (the scorer's raw
  cross-encoder score) and structural descendant mass (the provenance
  walk) -- through a MEASURED calibrator, sigma(A*sim + B*mass + C).
  A and C are measured against the live scorer (indisputable seed
  references scored at first boot; drift-triggered re-measurement --
  reranker-only, no generative calls). B is a DECLARED structural
  constant: the lift's magnitude has no label-free ground truth, and no
  oracle runs inside the substrate to invent one -- generative judgment
  belongs to the chat path exclusively; the substrate is non-generative
  end to end. The zero-mass floor is this law evaluated at mass = 0, not
  a second rule.
- **LossRatio** is the precision stance -- V_harm/(V_gain+V_harm) -- the
  one honest hand-set scalar: a value judgment, not derivable from data.
- **mu** is the token budget's shadow price, READ OFF the assembly shed
  equilibrium, never set: exactly zero whenever the budget has slack
  (complementary slackness), and the marginal refused DENSITY (excess P
  per wire token) when the budget binds. The shed ranks by density --
  greedy knapsack, so a marginally-better giant can no longer crowd out
  several cheap goods -- and the thread's next selection charges each
  candidate mu times its delivery-cost lower bound. Selection is the price
  filter; the shed is the hard enforcer; a one-call-stale price can never
  overrun the budget. Warm-started dual feedback: no fixpoint, no knob.
- **Diversity is not a knob**: a candidate's effective value is its NOVEL
  FRACTION -- value * (1 - max similarity to the already-kept) -- a
  derived form with zero free parameters.

Resource rules vs truth rules: caps and cadences (the provenance walk's
compute cap) are permissible resource rules -- but
WHAT they keep must follow the law's own currency (the walk truncates
best-first by path-product bound into the anchor set, never by hop order),
and truncation is always instrumented, never silent.

==== Bounded Selective Assembly

Zero-return is valid. If no candidate clears calibrated acceptance, the prompt is novel and the model receives it without augmentation.

=== Payload Assembly

==== Subgraph Extraction

Best-first backward traversal from the prompt through the prerequisite DAG:

1. Apply thread scope filter: if thread-scoped, only follow edges within the prompt's thread. If all-threads, traverse the full global DAG.
2. Seed priority queue with direct prerequisites of the prompt, ordered by edge score
3. Pop highest-score message, add to selection
4. Push its prerequisites with multiplicatively decayed scores (effective_score = edge_score * parent_score)
5. Repeat until queue empty or effective score falls below score floor (default 0.01, configurable)
6. Return the full ranked selection to the service

**Score floor derivation:** At average edge score 0.7, multiplicative decay reaches 0.01 at ~12 hops. At 0.6, ~8 hops. Depth adapts to edge quality -- stronger prerequisite chains traverse deeper, weaker chains self-terminate sooner. 0.01 means less than 1% of the maximum possible score -- below practical significance for selection ranking. No fixed depth limit; the math is the limit.

Thread scoping is a traversal filter on the global DAG — not a separate data structure or mechanism. The DAG contains all edges across all threads. The scope parameter determines which edges are followed.

The engine does not enforce a token budget. It selects based on dependency and returns a ranked list. The service decides payload size based on model-specific constraints -- the engine is agnostic to model context windows and tokenizers.

==== Transitive Reduction

Computed on demand over the selected subgraph, not maintained globally. The selected subgraph is small (typically 5-30 messages); reduction is trivial.

Removes redundant edges: if A->B->C and A->C, remove A->C from the selection. The minimal chain is what the model needs.

==== Native Format Restoration (service responsibility)

The engine returns ranked message IDs and scores in `SelectionResult`. The service looks up message content and orders selected messages chronologically, placing them in the model's input as ordinary conversation entries. No template, no label. Structurally indistinguishable from session history. This is the service's job -- the engine does not hold message content, only IDs, edges, and scores.

=== RRC in the Agent Loop

Every LLM call is an RRC selection event. Every LLM response is a carry-forward event. In an agentic tool chain, these compound across rounds.

==== Per-Round Cycle

A single user interaction may produce N rounds of tool calling. Each round is a full RRC cycle:

----
Round 1:
  RRC select → forward to LLM → response (thinking + tool calls)
  → carry-forward from thinking → execute tools → tool results become new messages

Round 2:
  RRC select (now informed by round 1 carry-forward) → forward to LLM → response (thinking + tool calls)
  → carry-forward from thinking → execute tools → tool results become new messages

Round N:
  RRC select (informed by rounds 1..N-1 carry-forward) → forward to LLM → response (thinking + final answer)
  → carry-forward from thinking
----

Every LLM response -- whether it ends with tool calls or a final answer -- contains thinking blocks. Every thinking block is carry-forward material. The engine improves WITHIN a single user interaction, not just across interactions.

Round 10's selection is informed by 9 rounds of the model's own reasoning fed back through the QUD graph and DAG. The selection gets sharper each round as the engine learns what the model finds relevant.

==== Why This Matters

Agentic tool chains produce growing conversation histories. The standard approach (send full history every round) hits the context window and must compact -- losing information. RRC selects fresh every round from the full lossless corpus. No compaction. No information loss. And the selection is informed by carry-forward that compounds across rounds.

==== Selection Events

An RRC selection event occurs before every LLM call:

- User sends a message → RRC selects → LLM call
- Tool results ready → RRC selects → LLM call
- Multiple tool results from one round → batched into one message → one RRC selection → one LLM call

The number of selections per user interaction is 1 + N where N is the number of tool rounds.

=== Warm Carry-Forward

The service parses every LLM response stream and feeds extracted content back to the engine. The engine never calls an LLM directly.

==== Response Reasoning Extraction

Every LLM response contains thinking blocks -- reasoning about why it's calling tools, what it expects to find, what prior context it's drawing on, what questions it's addressing. This reasoning reveals the conversation's dependency structure from the model's perspective.

The service extracts thinking blocks from the response stream and passes them to the engine. This happens every round, not just at the end of a tool chain.

==== QUD Graph Update

Two extraction paths from thinking blocks:

**Edge discovery (cross-encoder):** The thinking block text is scored against prior messages using the same cross-encoder that scores regular messages. If the model's reasoning references "the auth module we discussed," the cross-encoder scores (thinking_text, message_i) and finds the relevant messages. New edges added to the DAG.

**QUD extraction (small fast model):** The thinking blocks are passed to the small fast model (via the engine's Completer interface, injected at construction) to extract structured QUD operations: questions raised, questions addressed, status updates. This is a natural language understanding task that requires more than pattern matching.

Enrichment is additive only -- it adds edges and updates QUD status toward resolution. It never removes edges or re-opens resolved QUDs. This prevents oscillation.

==== Compounding

The carry-forward is "warm" because it compounds:

1. RRC selects prerequisites, forwards to LLM
2. LLM reasons about the conversation, responds with thinking + tool calls
3. Thinking blocks reveal what the model found relevant
4. Engine updates QUD graph and DAG with these signals
5. Tools execute, results become new messages
6. Next round's RRC selection is informed by steps 3-4
7. Repeat -- each round benefits from all prior rounds' reasoning

The model's own reasoning is a signal source for the prerequisite graph. Within a single tool chain, the system gets progressively better at selecting what the model needs.
