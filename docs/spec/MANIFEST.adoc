== Context

=== Identity

*Name:* {project-name}

*Paradigm:* {project-paradigm}

{project-name} is an agentic software system built natively for {rrc-full} (RRC). Four concerns, four specs:

1. **Core Library** (`spec/core`) -- A Go library providing provider-agnostic abstractions for language models, embeddings, and scorers. Proto definitions are the truth types. The foundational dependency. Everything else is a consumer.

2. **RRC Engine** (`spec/rrc`) -- A Go library implementing the {rrc-full} algorithm. Prerequisite detection, selection scoring, payload assembly, native format restoration, warm carry-forward. Stateful when the service provides persistent data structures (agent path), stateless when called per-request (proxy path). No HTTP, no UI, no opinions about deployment. Depends on proto types only -- not on core. Defines its own consumer interfaces (Scorer, Completer). Imported by the service.

3. **Service** (`spec/service`) -- The application. A system tray process that runs the RRC engine as an LLM proxy, handles agent orchestration via {agent-framework}, manages thread storage, exposes a {api-protocol} API, and serves the web UI on `grudge.localhost:8420`. One binary. The user opens their browser.

4. **Web UI** (`spec/web`) -- A {ui-framework} application providing the agentic interface -- not a chat clone. Full RRC introspection: what was selected, excluded, prerequisite scores, prompt derivation. Agent state, tool visualization, execution traces. Served by the service on localhost; the user opens a browser tab. UX is a first-class spec concern.

==== Code Generation Philosophy

Code generation is a first-class architectural concern. The primary reason is maintainability: when truth types change, downstream code regenerates. No manual sync. This extends to generating bindings for different codebases and languages. It also establishes a single source of truth -- proto definitions generate Go types, {api-protocol} schema, and TypeScript client types through one pipeline.

==== Agnostic Boundaries

The following are explicitly provider-agnostic behind abstraction interfaces:

- **Language Model** -- Any LLM (Claude, GPT, Gemini, Llama, Mistral, etc.)
- **Embedder** -- Any embedding model (TEI, OpenAI embeddings, Cohere, etc.)
- **Provider** -- Any serving infrastructure (Ollama, Anthropic API, OpenAI API, Google AI, vLLM, any OpenAI-compatible endpoint)

The core library defines the abstraction interfaces. Provider implementations are separate packages. "Just works" is the design target -- consumers interact with capabilities, never with provider specifics.

==== Development Environment

The development environment uses {dev-lm-runtime} for local language model serving and {dev-embedder-runtime} for local embedding. These are development tools, not product dependencies. The product is agnostic to both.

=== {rrc-full} (RRC)

LLMs are stateless. Every API call is an independent forward pass. The standard approach is brute force: the client sends the full conversation history every request. This works until attention dilutes across hundreds of messages and the model loses coherence.

RRC replaces brute force with selective assembly. The client sends its full conversation as it normally would. RRC intercepts that request, identifies which specific messages the current prompt depends on, and forwards only those to the model as native conversation entries. The model sees 10 messages instead of 500 -- the prerequisites for coherent continuation. It cannot tell the difference.

**RRC is not RAG.** RAG retrieves from external knowledge bases and injects labeled context ("here is relevant information"). RRC retrieves from the conversation the client already sent and restores native messages -- structurally indistinguishable from session history. Different corpus, different format, different model perception.

==== Four Properties

1. **Lossless corpus.** RRC expects the conversation it receives to be complete and unmodified. No summarization, no entity extraction upstream. This is a constraint on the client, not a service RRC provides. RRC does not own storage.
2. **Prerequisite detection.** Selection targets the messages the prompt depends on, not topically similar content. A 1000-message conversation has many messages about the same topic -- the prompt depends on maybe 3.
3. **Native format restoration.** Selected messages are placed in the model's input as ordinary conversation entries. No template, no label. The model processes them through standard attention.
4. **Bounded selective assembly.** Zero-return is valid -- the model is capable without augmentation for a novel prompt.

// end::rrc[]

==== Delivery Model

The service delivers RRC transparently. It runs a proxy that accepts standard LLM API requests from any client. The client sends its full conversation as it normally would. The proxy extracts the conversation, calls the RRC engine to select prerequisites and assemble the payload, then forwards the assembled payload to the upstream LLM. On the response path, the proxy parses the model's output stream and feeds extracted reasoning content back to the RRC engine for warm carry-forward.

The client does not change. The model does not know. Each request is independent.
