== Context

=== Identity

*Name:* {project-name} {module-name}

*Paradigm:* System Tray Application

The service is the application binary. It runs as a system tray process. Two distinct request flows share a common foundation:

==== Proxy Path (third-party clients)

A transparent RRC proxy. Third-party clients send standard LLM API requests -- they don't know the service exists. The proxy intercepts the request, calls the RRC engine to select prerequisites and assemble the payload, forwards to the upstream LLM, and streams the response back. On the return path, the proxy parses the response stream and feeds extracted reasoning content to the RRC engine for warm carry-forward.

- **Entry point:** HTTP endpoint (standard LLM API format)
- **State model:** Stateless per-request. The client owns its corpus and sends it every time.
- **Client awareness:** None. The client doesn't know RRC is involved.
- **Response:** Streamed passthrough. The client sees a normal LLM response.

==== Agent Path (native web UI)

An orchestrated agentic loop with full RRC introspection. The web UI issues {api-protocol} requests. The service runs the agent loop -- plan, call RRC engine, call LLM, execute tools, evaluate, decide next step. Conversation storage is persistent and server-owned. RRC introspection data (what was selected, excluded, scores, prompt derivation) flows back to the web UI via {api-protocol} subscriptions.

- **Entry point:** {api-protocol} API (queries, mutations, subscriptions)
- **State model:** Stateful. The service owns conversation history, agent state, and carry-forward cache.
- **Client awareness:** Full. The web UI sees everything RRC does.
- **Response:** Structured {api-protocol} responses + live subscriptions for streaming, agent state, and introspection.

==== Shared Foundation

Both paths share:

- **RRC engine** -- The same library instance handles prerequisite detection and payload assembly for both paths.
- **Conversation storage** -- The proxy path receives the corpus per-request from the client. The agent path reads from server-owned persistent storage. Both feed into the same RRC engine.
- **Provider routing** -- Both paths forward to the same upstream LLM, configured the same way.
- **Warm carry-forward** -- Reasoning extracted from LLM responses enriches future selection for both paths.

==== Service Infrastructure

Independent of either request flow:

- **System tray** -- Tray icon, lifecycle management, status indicators.
- **Service management UI** -- Lightweight config/status surface accessible from the tray. Not the agentic web UI.
- **Static asset serving** -- Serves the web UI on localhost. The user opens their browser.

=== Scope

==== In Scope

===== Proxy Path
- HTTP endpoint accepting standard LLM API requests
- Transparent forwarding via RRC engine
- Response stream parsing: SSE/chunked passthrough with concurrent extraction of reasoning content
- Stateless per-request handling (client provides corpus)

===== Agent Path
- {api-protocol} API: full schema and resolvers (orchestration, conversations, RRC introspection, config)
- {api-protocol} subscriptions: live agent state, streaming responses, RRC introspection during execution
- Agent orchestration: agent loop, planning, tool execution, self-correction
- Conversation storage: persistent, complete, unmodified history (lossless corpus guarantee)

===== Shared
- RRC engine integration (calling `spec/rrc` library for both paths)
- Provider routing: configuration for which upstream LLM to forward to
- Warm carry-forward cache management

===== Infrastructure
- System tray integration (Windows primary, cross-platform later)
- Service lifecycle: start, stop, health check, configuration
- Static asset serving: web UI files on localhost
- Service management UI: lightweight status/config accessible from tray

==== Out of Scope

- The RRC algorithm itself (belongs to `spec/rrc`; the service calls it)
- LLM/embedder interface or adapter definitions (belongs to `spec/core`)
- Proto truth type definitions (belongs to `spec/core`)
- Agentic UI, RRC introspection views, UX patterns (belongs to `spec/web`)
- Cloud deployment or multi-tenancy
