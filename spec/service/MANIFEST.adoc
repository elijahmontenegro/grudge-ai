== Context

=== Identity

*Name:* {project-name} {module-name}

*Paradigm:* System Tray Application

The service is the application binary. It runs as a system tray process. Two distinct request flows share a common foundation:

==== Proxy Path (third-party clients)

A transparent RRC proxy. Third-party clients send standard LLM API requests -- they don't know the service exists. The proxy intercepts the request, runs the RRC engine statelessly (score, select, assemble), forwards to the upstream LLM, and streams the response back. Nothing persists. No DAG, no QUD graph, no carry-forward accumulation. Each request is independent.

- **Entry point:** HTTP endpoint (standard LLM API format)
- **State model:** Stateless. The client owns its corpus and sends it every time. The proxy does not store messages, scores, or edges across requests.
- **Client awareness:** None. The client doesn't know RRC is involved.
- **Response:** Streamed passthrough. The client sees a normal LLM response.

==== Agent Path (native web UI)

Orchestrated by Google ADK (Agent Development Kit) Go. The RRC engine integrates as an implementation of ADK's `model.LLM` interface -- ADK calls what it thinks is an LLM, and RRC intercepts transparently. Same pattern as the proxy path: the caller doesn't change, the model doesn't know.

ADK provides: agent orchestration (sequential, parallel, loop agents), tool system (function tools with auto-declaration, toolsets, MCP integration), plugin lifecycle hooks, session/event model with state management, multi-agent patterns with agent transfer.

RRC provides: prerequisite selection on every LLM call, carry-forward on every LLM response, compounding within tool chains. ADK doesn't know this is happening.

The web UI issues {api-protocol} requests. ADK runs the agent loop. RRC sits between ADK and the LLM. Thread storage is persistent and server-owned. RRC introspection data flows to the web UI via {api-protocol} subscriptions.

- **Entry point:** {api-protocol} API (queries, mutations, subscriptions)
- **State model:** Stateful. The service owns thread history, agent state, carry-forward cache, and ADK session state.
- **Client awareness:** Full. The web UI sees everything RRC does.
- **Response:** Structured {api-protocol} responses + live subscriptions for streaming, agent state, and introspection.

==== Shared Foundation

Both paths share:

- **RRC engine** -- The same engine code, two modes. The proxy path runs it statelessly (no persistence). The agent path runs it statefully (global DAG, per-thread QUD, compounding carry-forward).
- **Provider routing** -- Both paths forward to the same upstream LLM, configured the same way.

==== Subagents (Ephemeral Thread Forks)

A subagent is an ephemeral thread fork. The parent model spawns it with a task via ADK's AgentTool. The subagent inherits a snapshot of the parent thread's DAG and score cache at fork time — warm start. It runs RRC per-event against its own forked corpus (parent's messages at fork time + its own new messages). Its carry-forward builds its own QUD graph — identity diverges from the parent through its own reasoning trajectory.

When the subagent finishes, its messages and DAG edges merge back into the parent's corpus. The subagent's intermediate work (file reads, analysis, tool results) is available for future selection in the parent thread. Like a git branch that merges back — the work product reunites. The cross-encoder scores from the subagent transfer (messages are immutable, scores are valid). The parent only needs to score the subagent's messages against any parent messages that arrived after the fork.

The subagent's result enters the parent thread as a message. In the UI, the subagent's intermediate work is collapsible — the user sees the result inline, expands to see the process.

ADK agent types map to this model:

- **AgentTool** -- Ephemeral thread fork. Task in, result out. Messages merge back.
- **ParallelAgent** -- Multiple forks running concurrently. Each fork has its own RRC state. All merge back on completion.
- **LoopAgent** -- Sequential execution within the same thread. No fork needed.
- **SendMessage** -- Message a running fork. The fork continues with the new input. Another RRC selection event in the fork.

==== Plan Mode

A permission state transition. The service switches the agent to read-only mode: write tools (FileEdit, FileWrite, Bash write ops) are disabled, read tools (FileRead, Glob, Grep, Bash read ops, WebSearch, WebFetch) remain available. The agent explores the codebase and designs an implementation approach.

**Lifecycle:**

1. **Enter:** `EnterPlanMode` tool call. Service transitions permission state to `plan`. Write tools disabled. Plan mode prompt section included. Agent explores using read-only tools.
2. **Explore:** Agent reads code, searches for patterns, identifies critical files. Multiple turns of exploration before designing.
3. **Write plan:** Agent creates a plan directory -- `$XDG_DATA_HOME/spidey/plans/{slug}/` with `plan.adoc` as the entry point. Slug generated per plan (human-readable, unique per thread). The agent writes the plan and supporting artifacts (research notes, code analysis, architectural findings from the exploration phase). AsciiDoc `include::` directives compose artifacts into the plan. The agent builds the directory; the service creates it on first write.
4. **Exit:** `ExitPlanMode` tool call. Service compiles the plan directory (resolves includes) and surfaces it to the user in the web UI for review. User approves, optionally edits, or rejects.
5. **Post-approval:** Service restores previous permission state (write tools re-enabled). Plan content enters the thread as a message (available for RRC selection). Plan file persists on disk. Plan content injected as per-turn prompt section -- the agent sees the plan on every subsequent request.

The plan is a design artifact, not a project management tool. The agent reads the plan and implements. There is no step-by-step status tracking. Progress is implicit in the work being done.

**Plan format:** AsciiDoc directory -- the project's document regime. The agent writes structured sections (objective, approach, steps, critical files). No prescribed schema -- the agent structures the plan as the design requires. Supporting artifacts from the exploration phase compose into the plan via `include::` directives.

Example plan directory:

----
plans/implement-auth/
├── plan.adoc              # Entry point
├── research.adoc          # Exploration findings
└── existing-patterns.adoc # Code patterns found during exploration
----

**RRC integration:** The approved plan enters the thread as a message. RRC selects it as a prerequisite during execution. Carry-forward captures the model's reasoning about the plan. The plan's influence on selection compounds across rounds.

**Re-entry:** If the agent re-enters plan mode after exiting, the existing plan file is available for revision. The previous plan remains in the thread corpus for RRC.

==== Autonomous Mode

The agent loop normally exits when the model's response contains no tool calls (stop reason: end_turn). Autonomous mode overrides this. The loop does not exit. The service runs another RRC round.

The model's response is now in the corpus. Carry-forward happened. The engine selects fresh prerequisites. The model gets called again with this new selection and an empty user message — the same pattern as tool results returning with no user text. The model continues from context alone. Its reasoning drives the direction.

No continuation prompt. No injected instructions. The selection IS the context. The carry-forward shaped the selection. The model's own prior thinking shaped the carry-forward. The model drives itself through its own accumulated reasoning.

Emergent behavior is the feature. The model finishes a task, gets another round, and reasons about what comes next — review, edge cases, documentation, pivoting to something it noticed. The direction is not prescribed.

- **Duration:** Freeform `time.Duration` with 2-week maximum. The loop exits when the timer expires or the user stops it.
- **Controls:** Play (start), Pause (halt — user reviews, course corrects, resumes), Stop (end autonomous mode).
- **Thread state:** A thread in autonomous mode shows its running state, elapsed time, and round count. Visible from the thread list.

==== Payload Sizing

The RRC engine returns a ranked selection -- every message that passes the score threshold, ordered by effective score. The engine is agnostic to model context windows and tokenizers. The service decides how many messages to actually send.

The service sends the full selection to the LLM. If the model returns a context-length error, the service drops the lowest-scored message from the selection and retries. Repeat until the payload fits. Error-driven backoff -- no tokenizer, no estimation, no guessing. The model tells you when it's too much.

==== Platform Paths (XDG Base Directory Specification)

Spidey follows XDG for all platform paths:

- **Config:** `$XDG_CONFIG_HOME/spidey/` (settings, provider config, permissions)
- **Data:** `$XDG_DATA_HOME/spidey/` (SQLite database, threads, plans, skills)
- **Cache:** `$XDG_CACHE_HOME/spidey/` (memoized prompt sections, temporary artifacts)

==== Prompt Templates (PEaC -- Prompt Engineering as Code)

System prompts are composed from independent sections -- each section is a Go `text/template` file (`.tmpl`) in the `templates/` directory. Version controlled. Programmatically assembled at runtime. Each section memoized independently. The composition IS the prompt architecture.

**Composition model:** `system.tmpl` is the entry point. It includes section templates. Sections are independently authored, versioned, and testable. Mode changes (plan, autonomous, normal) are section inclusion/exclusion decisions -- not separate templates. Section content and inventory are implementation artifacts that evolve with tuning.

**Section categories:**

Stable sections (memoized, recomputed on config change or thread switch):

- User identity: full name, preferences (from onboarding)
- System: OS, available tools
- Thread context: mounted directories, thread name
- SPIDEY.md: project-level instructions from mounted directories

Per-turn sections (recomputed each request):

- Current time
- Active plan content (if plan exists)

Mode-conditional sections (included based on permission state):

- Plan mode instructions (included when permission state is `plan`)
- RRC context (the model's context is RRC-selected -- always included)

Templates are not user-facing. They are engineering artifacts maintained in the codebase.

**Design principle: don't put discoverable information in the prompt.** The system prompt contains only what the model cannot figure out on its own. User identity, thread name, mounted directories, SPIDEY.md instructions, active plan content -- these are non-discoverable. Git status, file trees, directory listings, file contents -- the model discovers these through tools. The prompt is lean.

==== SPIDEY.md

Any mounted directory can contain a `SPIDEY.md` file. The template system picks it up automatically and injects its content into the system prompt. Project-level instructions without configuration. Multiple mounted directories can each have their own `SPIDEY.md` — all are injected. This is the abstraction for project-specific prompt injection: drop a file, it works.

==== User Profile

User identity lives in the system prompt as a stable section. Captured during onboarding, injected into prompt templates on every request. Updated from time to time — by the user directly or via the small fast model when it detects relevant preference changes. Not a memory system. A supplementary system instruction that evolves.

==== Skills

Markdown files with YAML frontmatter. User-extensible capabilities — domain-specific instructions, workflows, constraints.

Loaded from (priority order):

1. Bundled (shipped with Spidey in the binary)
2. User (`$XDG_DATA_HOME/spidey/skills/`)
3. Project (`.spidey/skills/` in mounted directory)

Invoked from the web UI. Skill content is injected as message content (not system prompt) with argument substitution. Inline shell execution runs in the thread's sandbox.

Users create custom skills by dropping a markdown file in the skills directory. Frontmatter specifies: name, description, when to use, allowed tools, arguments.

==== Hooks

Lifecycle event handlers. Shell commands or scripts executed on events. Escape hatches for automation without modifying core code.

Events:

- `PreToolUse` / `PostToolUse` -- before/after tool execution
- `ThreadStart` / `ThreadEnd` -- thread lifecycle
- `PreCarryForward` / `PostCarryForward` -- before/after thinking block processing (RRC-specific)
- `UserPromptSubmit` -- before a user message enters the agent loop

A hook can: block a tool call (agent sees denial), modify tool input, inject context, or run silently.

Configured in settings (`$XDG_CONFIG_HOME/spidey/settings.json`), per-thread or global. Trust-gated — hooks only execute after workspace trust is accepted.

==== Plans

Plans are living AsciiDoc artifact directories, not messages. Per-plan: `$XDG_DATA_HOME/spidey/plans/{slug}/` with `plan.adoc` as entry point. Slug generated per plan (human-readable word slug, unique per thread). The directory contains the plan and supporting artifacts from the exploration phase, composed via AsciiDoc `include::` directives. See Plan Mode (above) for the full lifecycle and RRC integration.

==== Thread Workspaces

Each thread has one or more mounted directories. A thread isn't just a conversation — it's a workspace. File operations, git, code execution are scoped to the mounted directories. Directories are mutable — add or remove over the thread's lifetime.

Mounted directories are injected into the system prompt template. Different threads, different directories, potentially different git repos.

==== Docker Sandboxes

Tool execution (shell commands, code execution, file writes) runs in Docker Sandboxes by default. The thread's mounted directories are volumes in the sandbox — the agent operates on real files but in isolation from the host.

Sandboxed by default. Per-thread opt-out for advanced users who need direct host access. The `Thread` proto carries a `sandboxed` flag.

==== Tool Permissions

Tools are permission-gated. The agent cannot execute a tool without authorization. ADK provides `before_tool_callback` in its plugin system — every tool call is intercepted before execution.

Permission levels:

- **Allow** -- Tool executes without prompting.
- **Ask** -- User is prompted before execution. The web UI shows the pending tool call, user approves or denies.
- **Deny** -- Tool is blocked. User or policy has forbidden it.

Default permission set: read-only tools (file read, glob, grep, search) → Allow. Write tools (file edit, write, bash, code execution) → Ask. Destructive tools (rm, git push) → Ask with warning.

Permissions are configurable per-thread. A thread working on a production codebase might deny destructive operations. A sandbox thread might allow everything. The sandbox itself provides a safety boundary — even "allow all" is contained.

The default permission set: read tools allowed, write tools ask, destructive tools (rm, git push, etc.) ask with warning.

**Auto-approve mode:** A permission mode where configured tool categories are pre-approved without prompting. For users who want reduced friction without full autonomous mode. Configured per-thread — which tools auto-approve, which still ask. Autonomous mode implies auto-approve for all tools. Auto-approve without autonomous means the user is still driving, just with fewer interruptions.

==== Model Roles

The service configures three model roles:

- **Main model** -- The user's LLM. Reasoning, tool use, responses. Configured by the user (Anthropic, OpenAI, Ollama, etc.).
- **Cross-encoder** -- NLI model for pairwise dependency scoring. The Classifier interface is provider-agnostic. Development environment uses TEI.
- **Small fast model** -- Internal utility. QUD extraction from thinking blocks, annotations, autocomplete, tool rationale. User configures during onboarding -- same Completer interface and provider selection as the main model. Sub-second latency required for autocomplete; multi-second acceptable for QUD extraction. Recommended models: sub-1B extraction-focused (Osmosis-Structure-0.6B, NuExtract-tiny, Qwen3.5-0.8B). Autocomplete uses a per-thread store of user input history as context -- the small model predicts likely next input based on thread context and input history.

All three use provider-agnostic interfaces (Completer for main + small fast, Classifier for cross-encoder). The RRC engine defines its own consumer interfaces that any core adapter satisfies via Go structural typing.

==== First Run

On first launch, the service probes localhost for default provider endpoints (Ollama at default port, TEI at default port). If detected, the web UI shows detected providers for user confirmation. If not detected, the web UI shows a setup form for endpoint URLs, model selection, and API keys.

All three model roles must be configured. The system does not start without them. RRC is not optional -- there is no degraded mode or passthrough fallback.

==== Error Policy

- **LLM provider unreachable:** Error shown in the active thread. Agent pauses. User can retry or reconfigure.
- **Cross-encoder unreachable:** System does not function. Error displayed prominently. Links to settings. System waits until resolved.
- **Context-length error:** Error-driven backoff -- drop lowest-scored message, retry. Transparent to user.
- **Autonomous run failure:** Agent pauses with error state. User reviews, retries, or stops.

==== Service Infrastructure

Independent of either request flow:

- **System tray** -- Cross-platform via {tray-lib}. Tray icon (spider), lifecycle management, status indicators. On launch: service starts, tray icon appears, browser opens automatically to `spidey.localhost:{port}`. Context menu: Open Spidey, Settings, Quit Spidey. Double-click opens browser.
- **Local DNS** -- The service binds to `spidey.localhost:{port}` (RFC 6761 reserves `.localhost` for loopback; modern browsers resolve it natively). Port {port} avoids elevated privileges required by port 80. No DNS configuration needed.
- **Static asset serving** -- Serves the web UI at `spidey.localhost:{port}`. The browser opens automatically on launch.

=== Scope

==== In Scope

===== Proxy Path
- HTTP endpoint accepting LLM API requests in any format the core library has an adapter for (Anthropic Messages, OpenAI Chat Completions, Ollama, etc.)
- The client does not change -- it sends requests in its native format, the proxy accepts and translates via core provider adapters
- Transparent forwarding via RRC engine (stateless mode)
- Response stream parsing: passthrough with concurrent extraction of reasoning content
- Stateless per-request handling (client provides corpus)

===== Agent Path
- {api-protocol} API: full schema and resolvers (orchestration, threads, RRC introspection, config)
- {api-protocol} subscriptions: live agent state, streaming responses, RRC introspection during execution
- Agent orchestration via ADK Go: LlmAgent, SequentialAgent, ParallelAgent, LoopAgent, agent transfer
- Tool system via ADK Go: FunctionTool (auto-declaration from Go functions), Toolset (dynamic tool groups), MCP integration
- Built-in tools: Bash, FileRead, FileEdit, FileWrite, Glob, Grep, NotebookEdit, WebSearch, WebFetch, AskUserQuestion, Skill, TodoWrite, EnterPlanMode, ExitPlanMode. All execute in thread's Docker sandbox.
- Agent tools: Agent (spawn subagent as ephemeral thread fork), SendMessage (message a running subagent), TaskCreate/Get/Update/List/Stop/Output (task management)
- MCP tools: dynamic tools from configured MCP servers via ADK's McpToolset
- Plugin system via ADK Go: lifecycle hooks (before/after agent, model, tool execution)
- Thread storage: persistent, complete, unmodified history (lossless corpus guarantee)
- RRC-as-LLM adapter: implements ADK's `model.LLM` interface, routes through RRC engine to actual LLM via core Completer
- Warm carry-forward: extract thinking blocks from every LLM response, pass to RRC engine as `CarryForwardInput` (proto), engine runs edge discovery (cross-encoder on thinking text) and QUD extraction (small fast model)
- Autonomous mode: override model stop reason, continue running RRC rounds with empty user message, duration timer, play/pause/stop controls

===== Shared
- RRC engine integration (calling `spec/rrc` library — stateful for agent path, stateless for proxy path)
- Provider routing: configuration for which upstream LLM to forward to

===== Infrastructure
- Cross-platform system tray via {tray-lib} (macOS, Linux, Windows)
- Service lifecycle: start, stop, health check, configuration
- Static asset serving: web UI files on localhost
- Service management UI: lightweight status/config accessible from tray

==== EnterPlanMode

Transitions permission state to `plan`. Write tools disabled, read tools remain available. The agent uses this proactively when the task is non-trivial: multiple possible approaches, architectural decisions, multi-file changes, unclear requirements. The agent does NOT use this for trivial changes, single-line fixes, or pure research.

On entry: plan mode prompt section included (mode-conditional section in template composition). Previous permission state saved for restoration on exit.

==== ExitPlanMode

Compiles the plan directory (`$XDG_DATA_HOME/spidey/plans/{slug}/plan.adoc`, resolving includes). Surfaces compiled plan to user in web UI for review. User approves (optionally edits) or rejects.

On approval: restores previous permission state. Plan content enters thread as a corpus message (available for RRC selection). Plan file persists on disk. Plan injected as per-turn prompt section. If plan is empty: user approved exiting plan mode without a plan (valid -- the exploration itself was the value).

==== Plan Mode Tool Availability

In plan mode, only read-category tools + AskUserQuestion are available. All write, destructive, agent, and skill tools are disabled. The agent can write ONLY to the plan file.

=== {api-protocol} Schema

=== SQLite Schema

Single embedded database at `$XDG_DATA_HOME/spidey/spidey.db`. WAL mode. Single connection pool.

    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    sandboxed BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE thread_working_dirs (
    thread_id TEXT NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
    path TEXT NOT NULL,
    PRIMARY KEY (thread_id, path)

CREATE TABLE messages (
    id TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL REFERENCES threads(id) ON DELETE CASCADE,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP

CREATE INDEX idx_messages_thread_position ON messages(thread_id, position);

    from_message_id TEXT NOT NULL,
    to_message_id TEXT NOT NULL,

=== Concurrency

- **RWMutex** on global DAG and score cache: concurrent reads during selection, exclusive writes during scoring.
- **Per-thread QUD graphs** are naturally isolated (one thread = one QUD graph = no contention).
- **SQLite WAL mode**, single connection pool. Concurrent readers, single writer.
- **Agent loop** sequential per thread. One active LLM call per thread at a time.
- **Goroutine-per-request** for proxy path (stateless, no shared state between requests).
- **Subagents** run in separate goroutines. Fork creates an isolated Engine copy. No shared mutable state between parent and fork during execution. Merge acquires write lock on parent's data structures.

=== Error Handling

Fail fast. No retries except payload sizing backoff (error-driven, not failure masking).

- **Proxy path:** Map upstream HTTP status codes. 200 on success. 502 on provider unreachable. 504 on provider timeout. 422 on context-length error (after backoff exhaustion).
- **{api-protocol} path:** Standard {api-protocol} error extensions with error type field. Error types: `PROVIDER_UNAVAILABLE`, `CLASSIFIER_UNAVAILABLE`, `CONTEXT_LENGTH`, `TOOL_DENIED`, `AGENT_ERROR`.
- **Subscription errors:** Error event pushed via subscription. Client displays inline in thread.

=== Performance

Performance optimization is explicitly deferred. Correctness and completeness are the targets. O(N) pairwise scoring per message arrival is the accepted cost of prerequisite detection accuracy. Complexity bounds are stated in `spec/rrc`. The system may be slow; it must not be wrong.
