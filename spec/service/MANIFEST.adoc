== Context

=== Identity

*Name:* {project-name} {module-name}

*Paradigm:* System Tray Application

The service is the application binary. It runs as a system tray process. Two distinct request flows share a common foundation:

==== Proxy Path (third-party clients)

A transparent RRC proxy. Third-party clients send standard LLM API requests -- they don't know the service exists. The proxy intercepts the request, runs the RRC engine statelessly (score, select, assemble), forwards to the upstream LLM, and streams the response back. Nothing persists. No DAG, no QUD graph, no carry-forward accumulation. Each request is independent.

- **Entry point:** HTTP endpoint (standard LLM API format)
- **State model:** Stateless. The client owns its corpus and sends it every time. The proxy does not store messages, scores, or edges across requests.
- **Client awareness:** None. The client doesn't know RRC is involved.
- **Response:** Streamed passthrough. The client sees a normal LLM response.

==== Agent Path (native web UI)

Orchestrated by Google ADK (Agent Development Kit) Go. The RRC engine integrates as an implementation of ADK's `model.LLM` interface -- ADK calls what it thinks is an LLM, and RRC intercepts transparently. Same pattern as the proxy path: the caller doesn't change, the model doesn't know.

ADK provides: agent orchestration (sequential, parallel, loop agents), tool system (function tools with auto-declaration, toolsets, MCP integration), plugin lifecycle hooks, session/event model with state management, multi-agent patterns with agent transfer.

RRC provides: prerequisite selection on every LLM call, carry-forward on every LLM response, compounding within tool chains. ADK doesn't know this is happening.

The web UI issues {api-protocol} requests. ADK runs the agent loop. RRC sits between ADK and the LLM. Thread storage is persistent and server-owned. RRC introspection data flows to the web UI via {api-protocol} subscriptions.

- **Entry point:** {api-protocol} API (queries, mutations, subscriptions)
- **State model:** Stateful. The service owns thread history, agent state, carry-forward cache, and ADK session state.
- **Client awareness:** Full. The web UI sees everything RRC does.
- **Response:** Structured {api-protocol} responses + live subscriptions for streaming, agent state, and introspection.

==== Shared Foundation

Both paths share:

- **RRC engine** -- The same engine code, two modes. The proxy path runs it statelessly (no persistence). The agent path runs it statefully (global DAG, per-thread QUD, compounding carry-forward).
- **Provider routing** -- Both paths forward to the same upstream LLM, configured the same way.

==== Plan Mode

The agent reasons without executing tools. Tools are unavailable — the model can only think and produce a structured plan (steps with dependencies). The plan is a message in the thread. On approval, the service restores tools and the agent executes.

RRC selects the plan as a prerequisite during execution. The plan persists in context through carry-forward across rounds — the agent maintains coherence with the plan even in long autonomous runs.

==== Autonomous Mode

The agent loop normally exits when the model's response contains no tool calls (stop reason: end_turn). Autonomous mode overrides this. The loop does not exit. The service runs another RRC round.

The model's response is now in the corpus. Carry-forward happened. The engine selects fresh prerequisites. The model gets called again with this new selection and an empty user message — the same pattern as tool results returning with no user text. The model continues from context alone. Its reasoning drives the direction.

No continuation prompt. No injected instructions. The selection IS the context. The carry-forward shaped the selection. The model's own prior thinking shaped the carry-forward. The model drives itself through its own accumulated reasoning.

Emergent behavior is the feature. The model finishes a task, gets another round, and reasons about what comes next — review, edge cases, documentation, pivoting to something it noticed. The direction is not prescribed.

- **Duration:** User-set timer (5m, 30m, 2h, 8h, up to 2w). The loop exits when the timer expires or the user stops it.
- **Controls:** Play (start), Pause (halt — user reviews, course corrects, resumes), Stop (end autonomous mode).
- **Thread state:** A thread in autonomous mode shows its running state, elapsed time, and round count. Visible from the thread list.

==== Payload Sizing

The RRC engine returns a ranked selection -- every message that passes the score threshold, ordered by effective score. The engine is agnostic to model context windows and tokenizers. The service decides how many messages to actually send.

The service sends the full selection to the LLM. If the model returns a context-length error, the service drops the lowest-scored message from the selection and retries. Repeat until the payload fits. Error-driven backoff -- no tokenizer, no estimation, no guessing. The model tells you when it's too much.

==== Prompt Templates

System prompts are Go `text/template` files (`.tmpl`) in the `templates/` directory. Version controlled artifacts, rendered at runtime with context injection:

- User identity: full name, preferences (from onboarding)
- Thread context: working directory, thread name
- Environment: current time, git status, file tree of working directory
- System: OS, available tools

Templates are not user-facing. They are engineering artifacts maintained in the codebase.

==== Onboarding

First-run captures user identity alongside provider configuration. Name and preferences are stored once and injected into prompt templates on every request. This is not a settings page — it's a one-time setup that shapes the model's understanding of who it's working with.

==== Thread Workspaces

Each thread has one or more mounted directories. A thread isn't just a conversation — it's a workspace. File operations, git, code execution are scoped to the mounted directories. Directories are mutable — add or remove over the thread's lifetime.

Mounted directories are injected into the system prompt template. Different threads, different directories, potentially different git repos.

==== Docker Sandboxes

Tool execution (shell commands, code execution, file writes) runs in Docker Sandboxes by default. The thread's mounted directories are volumes in the sandbox — the agent operates on real files but in isolation from the host.

Sandboxed by default. Per-thread opt-out for advanced users who need direct host access. The `Thread` proto carries a `sandboxed` flag.

==== Tool Permissions

Tools are permission-gated. The agent cannot execute a tool without authorization. ADK provides `before_tool_callback` in its plugin system — every tool call is intercepted before execution.

Permission levels:

- **Allow** -- Tool executes without prompting. Appropriate for read-only tools (file read, glob, grep, search).
- **Ask** -- User is prompted before execution. Appropriate for write tools (file edit, write, bash, code execution). The web UI shows the pending tool call, user approves or denies.
- **Deny** -- Tool is blocked. User or policy has forbidden it.

Permissions are configurable per-thread. A thread working on a production codebase might deny destructive operations. A sandbox thread might allow everything. The sandbox itself provides a safety boundary — even "allow all" is contained.

The default permission set: read tools allowed, write tools ask, destructive tools (rm, git push, etc.) ask with warning.

==== Model Roles

The service configures three model roles:

- **Main model** -- The user's LLM. Reasoning, tool use, responses. Configured by the user (Anthropic, OpenAI, Ollama, etc.).
- **Cross-encoder** -- NLI model for pairwise dependency scoring. Runs on TEI or equivalent classifier endpoint.
- **Small fast model** -- Internal utility. QUD extraction from thinking blocks, annotations, autocomplete, tool rationale. Near-free per call. Opinionated default (e.g., small model on user's Ollama) or user-configured.

All three use core's provider-agnostic interfaces (Completer for main + small fast, Classifier for cross-encoder).

==== First Run

On first launch, the service probes localhost for default provider endpoints (Ollama at default port, TEI at default port). If detected, the web UI shows detected providers for user confirmation. If not detected, the web UI shows a setup form for endpoint URLs, model selection, and API keys.

All three model roles must be configured. The system does not start without them. RRC is not optional -- there is no degraded mode or passthrough fallback.

==== Error Policy

- **LLM provider unreachable:** Error shown in the active thread. Agent pauses. User can retry or reconfigure.
- **Cross-encoder unreachable:** System does not function. Error displayed prominently. Links to settings. System waits until resolved.
- **Context-length error:** Error-driven backoff -- drop lowest-scored message, retry. Transparent to user.
- **Autonomous run failure:** Agent pauses with error state. User reviews, retries, or stops.

==== Service Infrastructure

Independent of either request flow:

- **System tray** -- Tray icon (spider), lifecycle management, status indicators. On launch: service starts, tray icon appears, browser opens automatically to `spidey.localhost`. Context menu: Open Spidey, Settings, Quit Spidey. Double-click opens browser.
- **Local DNS** -- The service binds to `spidey.localhost` (RFC 6761 reserves `.localhost` for loopback; modern browsers resolve it natively). No DNS configuration needed.
- **Static asset serving** -- Serves the web UI at `spidey.localhost`. The browser opens automatically on launch.

=== Scope

==== In Scope

===== Proxy Path
- HTTP endpoint accepting LLM API requests in any format the core library has an adapter for (Anthropic Messages, OpenAI Chat Completions, Ollama, etc.)
- The client does not change -- it sends requests in its native format, the proxy accepts and translates via core provider adapters
- Transparent forwarding via RRC engine (stateless mode)
- Response stream parsing: passthrough with concurrent extraction of reasoning content
- Stateless per-request handling (client provides corpus)

===== Agent Path
- {api-protocol} API: full schema and resolvers (orchestration, threads, RRC introspection, config)
- {api-protocol} subscriptions: live agent state, streaming responses, RRC introspection during execution
- Agent orchestration via ADK Go: LlmAgent, SequentialAgent, ParallelAgent, LoopAgent, agent transfer
- Tool system via ADK Go: FunctionTool (auto-declaration from Go functions), Toolset (dynamic tool groups), MCP integration
- Plugin system via ADK Go: lifecycle hooks (before/after agent, model, tool execution)
- Thread storage: persistent, complete, unmodified history (lossless corpus guarantee)
- RRC-as-LLM adapter: implements ADK's `model.LLM` interface, routes through RRC engine to actual LLM via core Completer
- Warm carry-forward: extract thinking blocks from every LLM response, pass to RRC engine as `CarryForwardInput` (proto), engine runs edge discovery (cross-encoder on thinking text) and QUD extraction (small fast model)
- Autonomous mode: override model stop reason, continue running RRC rounds with empty user message, duration timer, play/pause/stop controls

===== Shared
- RRC engine integration (calling `spec/rrc` library — stateful for agent path, stateless for proxy path)
- Provider routing: configuration for which upstream LLM to forward to

===== Infrastructure
- System tray integration (Windows primary, cross-platform later)
- Service lifecycle: start, stop, health check, configuration
- Static asset serving: web UI files on localhost
- Service management UI: lightweight status/config accessible from tray

==== Out of Scope

- The RRC algorithm itself (belongs to `spec/rrc`; the service calls it)
- LLM/classifier interface or adapter definitions (belongs to `spec/core`)
- Proto truth type definitions (belongs to `spec/core`)
- Agentic UI, RRC introspection views, UX patterns (belongs to `spec/web`)
- Cloud deployment or multi-tenancy
