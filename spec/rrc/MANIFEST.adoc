== Context

=== Identity

*Name:* {project-name} {module-name}

*Paradigm:* Algorithm Library (stateful or stateless depending on caller)

The RRC engine is a Go library implementing the {rrc-full} algorithm. It operates on data structures (prerequisite DAG, QUD graph, score cache) provided by the caller. The engine reads and writes these structures but does not own them.

Two modes:

- **Stateful (agent path):** The service provides persistent data structures. The DAG, score cache, and QUD graph accumulate across requests. Carry-forward compounds. This is the full RRC experience.
- **Stateless (proxy path):** The service provides ephemeral data structures per-request. The engine scores, selects, assembles, and returns. Nothing persists. Each request is independent.

The engine does not know which mode it's running in. It operates on whatever structures the caller provides.

=== Scope

==== In Scope

- Prerequisite detection: cross-encoder pairwise dependency classification on message arrival, scored globally across all threads
- QUD (Questions Under Discussion) graph: per-thread, built from warm carry-forward, not dedicated LLM calls
- Prerequisite DAG: global dual adjacency list, incremental edge construction, thread-scoped or global subgraph extraction
- Score cache operations: reading and writing cross-encoder pairwise scores (global)
- Warm carry-forward ingestion: accepting extracted reasoning from the service, updating QUD graph and DAG
- Selection scoring: score fusion (cross-encoder + QUD + temporal proximity), thresholds, ranking
- Payload assembly: best-first backward traversal, ranked selection, native format restoration
- Transitive reduction: computed on demand during subgraph extraction

==== Out of Scope

- Calling LLMs (the service makes LLM calls; the engine receives extracted reasoning via carry-forward)
- Ownership or persistence of data structures (belongs to `spec/service`)
- Response stream parsing (belongs to `spec/service`; the engine receives extracted reasoning)

== Implementation

=== Prerequisite Detection

==== Cross-Encoder Pairwise Dependency Classification

A single cross-encoder classifies the dependency relationship between two messages. One model, one forward pass per pair, via the core classifier interface.

When message M_n arrives, the cross-encoder evaluates every (M_i, M_n) pair for i < n — across ALL threads, not just the thread M_n belongs to. Scoring is global because dependency does not respect organizational boundaries. A message in "backend architecture" may depend on a decision made in "project planning." Each pair produces a dependency score. Pairs scoring above threshold become edges in the prerequisite DAG.

The cross-encoder captures multiple facets of dependency implicitly through a single classification:

- **Entity reference dependency** (coreference) -- "that function" in M_n refers to something defined in M_i
- **Discourse dependency** (elaboration, cause, instantiation) -- M_n elaborates on, is caused by, or instantiates M_i
- **Logical prerequisite** -- M_n cannot be understood without M_i

These are not separate operations. They are theoretical lenses from NLP research (coreference resolution, PDTB discourse relations, prerequisite chain learning) that explain WHY the cross-encoder's entailment signal captures dependency. The model does not know these categories exist. It takes two texts in, classifies their logical relationship, outputs class probabilities.

Off-the-shelf NLI (Natural Language Inference) cross-encoders classify: entailment, contradiction, neutral. Entailment approximates dependency. Contradiction approximates non-dependency. Neutral approximates unrelated. No fine-tuning required.

Research basis: NLI cross-encoders (DeBERTa-v3 family), PDTB discourse relation framework, coreference resolution (CODI-CRAC), prerequisite chain learning (Liang et al., Gordon et al.).

==== QUD (Questions Under Discussion) Graph

The QUD graph captures what the cross-encoder cannot: long-range structural dependency through a thread's question-answer flow.

Every message addresses an implicit question and may raise new ones. If message M_47 raises a question and message M_312 answers it, M_47 is a prerequisite of M_312 -- even if they share no surface similarity and the cross-encoder would not score them highly as a pair.

The QUD graph is NOT built by dedicated LLM calls. It builds organically from warm carry-forward. The model is already the best QUD analyzer in the system -- it reasons about the conversation on every request. Its thinking blocks expose reasoning that disambiguates and contains QUD information. Making that reasoning a signal source is the mechanism.

The QUD graph is per-thread. Carry-forward only enriches the thread where the prompt originated. This preserves thread identity -- each thread develops its own reasoning trajectory through its own QUD accumulation. The cross-encoder handles cross-thread dependency; the QUD graph handles within-thread structural flow.

The graph starts cold. First few requests have no carry-forward data -- the cross-encoder is the only signal. As the model responds and reasoning accumulates, QUD edges appear and the graph gets richer. Natural warm-up, no bootstrapping needed.

QUD graph state:

- QUDs: question text, established-by message, parent QUD, status (open/partially-addressed/resolved), addressed-by messages
- Active stack: open QUDs ordered by recency
- Resolved set: closed QUDs retained for graph completeness
- Derived edges: source message -> target message, via QUD, with type (establishes->addresses, raises->resolves)

Research basis: Roberts (1996) QUD stack theory, Riester (2019) QUD tree construction, Benz & Jasinskaja (2017) mapping discourse relations to QUD.

=== Data Structures

The engine operates on three data structures. The service owns their persistence; the engine reads and writes them. Scoring and the DAG are global (across all threads). The QUD graph is per-thread.

==== Score Cache (global)

Cross-encoder pairwise dependency scores across all threads. When message M_n arrives, the engine scores every (M_i, M_n) pair across all threads and writes results to the cache. At query time, scores are already available -- no cross-encoder inference needed.

Messages are immutable. Cached scores do not become stale.

==== QUD Graph (per-thread)

Structural compression of a thread's discourse flow. One QUD graph per thread. Built incrementally from warm carry-forward as the model responds within that thread. Carry-forward only enriches the originating thread's graph -- this preserves thread identity.

Starts empty per thread. Grows richer with use.

==== Prerequisite DAG (global)

The central data structure. Cross-encoder edges (global) and QUD edges (per-thread) both feed into it. The DAG spans all threads.

**Structure:** Dual adjacency list -- two indexes over the same edge set:

- **Backward:** message -> its prerequisites (messages it depends on). The primary traversal direction for RRC.
- **Forward:** message -> its dependents (messages that depend on it). Used for impact analysis and introspection.

Edges carry: source, target, score, detection source (cross-encoder, QUD, or both), timestamp.

Temporal ordering guarantees acyclicity: edges only point from earlier messages to later messages. No cycle detection needed.

The engine defines the in-memory structures. The service decides how to persist and restore them.

=== Selection Scoring

==== Score Fusion

Each prerequisite edge carries scores from the signals that produced it:

- **Cross-encoder dependency score** -- Entailment probability from the NLI cross-encoder. Range 0-1. Edge creation threshold: 0.5 (configurable). Below threshold, no edge is created.
- **QUD edge weight** -- Binary: 1 if a QUD edge exists (carry-forward discovered a connection), 0 if not. A QUD edge either exists or it doesn't.
- **Temporal proximity** -- `1 / (1 + distance)` where distance is message position difference. Adjacent messages ~0.5, 9 apart ~0.1, 99 apart ~0.01.

Score fusion formula:

----
score = w1 * cross_encoder_score + w2 * qud_weight + w3 * temporal_proximity
----

Starting weights: `w1=0.7, w2=0.2, w3=0.1`. Cross-encoder is the primary signal. QUD adds long-range edges the cross-encoder misses. Temporal is a weak positional prior. Weights are configurable.

==== Bounded Selective Assembly

Zero-return is valid. If no message scores above threshold, the prompt is novel and the model receives it without augmentation.

=== Payload Assembly

==== Subgraph Extraction

Best-first backward traversal from the prompt through the prerequisite DAG:

1. Apply thread scope filter: if thread-scoped, only follow edges within the prompt's thread. If all-threads, traverse the full global DAG.
2. Seed priority queue with direct prerequisites of the prompt, ordered by edge score
3. Pop highest-score message, add to selection
4. Push its prerequisites with multiplicatively decayed scores (effective_score = edge_score * parent_score)
5. Repeat until queue empty or depth limit reached
6. Return the full ranked selection to the service

Thread scoping is a traversal filter on the global DAG — not a separate data structure or mechanism. The DAG contains all edges across all threads. The scope parameter determines which edges are followed.

The engine does not enforce a token budget. It selects based on dependency and returns a ranked list. The service decides payload size based on model-specific constraints -- the engine is agnostic to model context windows and tokenizers.

==== Transitive Reduction

Computed on demand over the selected subgraph, not maintained globally. The selected subgraph is small (typically 5-30 messages); reduction is trivial.

Removes redundant edges: if A->B->C and A->C, remove A->C from the selection. The minimal chain is what the model needs.

==== Native Format Restoration

Selected messages are ordered chronologically and placed in the model's input as ordinary conversation entries. No template, no label. Structurally indistinguishable from session history.

=== RRC in the Agent Loop

Every LLM call is an RRC selection event. Every LLM response is a carry-forward event. In an agentic tool chain, these compound across rounds.

==== Per-Round Cycle

A single user interaction may produce N rounds of tool calling. Each round is a full RRC cycle:

----
Round 1:
  RRC select → forward to LLM → response (thinking + tool calls)
  → carry-forward from thinking → execute tools → tool results become new messages

Round 2:
  RRC select (now informed by round 1 carry-forward) → forward to LLM → response (thinking + tool calls)
  → carry-forward from thinking → execute tools → tool results become new messages

Round N:
  RRC select (informed by rounds 1..N-1 carry-forward) → forward to LLM → response (thinking + final answer)
  → carry-forward from thinking
----

Every LLM response -- whether it ends with tool calls or a final answer -- contains thinking blocks. Every thinking block is carry-forward material. The engine improves WITHIN a single user interaction, not just across interactions.

Round 10's selection is informed by 9 rounds of the model's own reasoning fed back through the QUD graph and DAG. The selection gets sharper each round as the engine learns what the model finds relevant.

==== Why This Matters

Agentic tool chains produce growing conversation histories. The standard approach (send full history every round) hits the context window and must compact -- losing information. RRC selects fresh every round from the full lossless corpus. No compaction. No information loss. And the selection is informed by carry-forward that compounds across rounds.

==== Selection Events

An RRC selection event occurs before every LLM call:

- User sends a message → RRC selects → LLM call
- Tool results ready → RRC selects → LLM call
- Multiple tool results from one round → batched into one message → one RRC selection → one LLM call

The number of selections per user interaction is 1 + N where N is the number of tool rounds.

=== Warm Carry-Forward

The service parses every LLM response stream and feeds extracted content back to the engine. The engine never calls an LLM directly.

==== Response Reasoning Extraction

Every LLM response contains thinking blocks -- reasoning about why it's calling tools, what it expects to find, what prior context it's drawing on, what questions it's addressing. This reasoning reveals the conversation's dependency structure from the model's perspective.

The service extracts thinking blocks from the response stream and passes them to the engine. This happens every round, not just at the end of a tool chain.

==== QUD Graph Update

Two extraction paths from thinking blocks:

**Edge discovery (cross-encoder):** The thinking block text is scored against prior messages using the same cross-encoder that scores regular messages. If the model's reasoning references "the auth module we discussed," the cross-encoder scores (thinking_text, message_i) and finds the relevant messages. New edges added to the DAG.

**QUD extraction (small fast model):** The thinking blocks are passed to the small fast model (via core Completer interface) to extract structured QUD operations: questions raised, questions addressed, status updates. This is a natural language understanding task that requires more than pattern matching. The small fast model is near-free per call, making it practical to run on every carry-forward event.

Enrichment is additive only -- it adds edges and updates QUD status toward resolution. It never removes edges or re-opens resolved QUDs. This prevents oscillation.

==== Compounding

The carry-forward is "warm" because it compounds:

1. RRC selects prerequisites, forwards to LLM
2. LLM reasons about the conversation, responds with thinking + tool calls
3. Thinking blocks reveal what the model found relevant
4. Engine updates QUD graph and DAG with these signals
5. Tools execute, results become new messages
6. Next round's RRC selection is informed by steps 3-4
7. Repeat -- each round benefits from all prior rounds' reasoning

The model's own reasoning is a signal source for the prerequisite graph. Within a single tool chain, the system gets progressively better at selecting what the model needs.
